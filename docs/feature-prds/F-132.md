### 06 · Six buttons had an invisible hover state

`hover:bg-gold hover:text-tehom` — and `--color-gold` resolves to cobalt
(`#1f2a8d`) in light mode, so hover painted near-black text on a blue field.
Measured **1.57:1**. The six are both **auth submits**, both **error-recovery**
buttons, and the soul-audit error CTA: the exact moments a reader cannot afford
a dead control.

Fixed with the remedy this codebase already uses twice (SA-047 for the chat
launcher, SA-080 for `.mock-btn`): a `.cta-solid` class painting **both halves**
explicitly per theme rather than trusting a token whose name lies about its
value. Light: cobalt on cream (~9.7:1). Dark: amber on deep ink (~7.9:1).
`:focus-visible` shares the rule, as it did before — keyboard users must not
lose the affordance the fix restores.

### 26 · Reading estimates on the day cards

Cards answered "how long is this?" only in days.
[Waking Up](https://mobbin.com/screens/ebca587a-c673-4ea4-8e73-8885604daee0)
puts a duration on every item in a course list, because "do I have time for this
right now" is the actual question at 6am.

`src/lib/reading-time.ts` derives minutes from the **`words` count already in
`audio-manifest.json`** — 535 of 575 devotionals — at 200wpm. Reusing that
avoids inventing a second index over the same corpus and avoids reading
`public/devotionals` at runtime, which returns nothing on Workers.

**The caveat is stated, not buried.** That count is of the _narration script_,
and the segmenter deliberately omits pull quotes, captions, CTAs and art blocks.
So this is a slight **underestimate** of the full page, not a measurement of it —
the right direction to be wrong in for a "do I have time" signal, and the reason
the label reads "min read" rather than a precise duration. Devotionals with no
entry render nothing: a missing estimate beats a fabricated one.

### 42 · The composing screen names its stages

Three dots and "Building your paths..." is honest but opaque, and the wait is
real work. [stoic.](https://mobbin.com/flows/948a7285-9f2f-46d1-8d82-32da2d4ce828)
lists its stages during the same kind of pause, which turns a ten-second wait
into something happening rather than something lagging.

The three stages are the ones the submit route actually performs, in order:
reading the input, matching it against the library, composing three paths from
retrieved Scripture.

**The timing is estimated and the code says so.** The compose is a single
request with no progress events, so this cannot instrument real stage
boundaries. Two rules keep it honest: the **last stage never self-completes**
(nothing is marked done that the component cannot observe), and the whole thing
unmounts the moment the request returns — so a false "finished" state is never
shown.

**A duplication closed along the way.** The component's own doc claimed it was
the single place this markup lived. That was true of the homepage only —
`/soul-audit` still carried an inline copy, so the named stages would have
landed on one surface and not the other. Both render the component now.
