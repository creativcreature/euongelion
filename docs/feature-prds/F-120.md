# F-120: Toggle icons flashed blue on touch, and stayed lit after the tap

## Metadata

- Feature ID: F-120
- Category: Platform
- Owner: founder
- Status: shipped (2026-08-17)
- Decision: SA-076
- Surfaces: site-wide shell, `/series`

## Problem

> "why does the toggle icons on mobile highlight blue on page load? fix it"

Two independent causes, both verified against the live site.

## 1. The browser's own tap highlight

`-webkit-tap-highlight-color` was **never set anywhere** in 14,000+ lines of
`globals.css`. Mobile WebKit and Chrome therefore paint their default
translucent blue rectangle over any tapped button or link.

On a design whose entire palette is cobalt, that reads as the control lighting
up blue — which is precisely the report.

Set to `transparent` on `html`. This is safe rather than an accessibility
regression: every one of these controls carries a real `:focus-visible` style,
and that is what keyboard users actually rely on. The tap highlight only ever
appears for touch, where it duplicates the control's own pressed state.

## 2. `:hover` fires on touch — and sticks

`@media (hover: hover)` appears **zero times** in the stylesheet, so every
`:hover` rule also matches on a touch device. On touch there is no pointer to
move away, so the hover state **persists after the tap** until the reader taps
something else.

The hover state for these particular controls is a solid fill:

```css
.mock-btn:is(:hover, :focus-visible),
.mock-icon-control:is(:hover, :focus-visible),
.mock-account-trigger:is(:hover, :focus-visible),
.mock-mobile-menu-toggle:is(:hover, :focus-visible) {
  background: var(--mock-blue);   /* cobalt */
  ...
}
```

So tapping a toggle left it filled cobalt indefinitely. Combined with cause 1,
a single tap produced a blue flash followed by a blue box that did not go away.

### The fix, and why it is shaped this way

A `@media (hover: none)` block restores the resting appearance. Three details
matter:

- **`:not(:focus-visible)`** — the fill is preserved for anyone who genuinely
  focuses the control with a keyboard, including on a touch device with a
  keyboard attached. Only the phantom hover is neutralised.
- **Scoped under `.mock-home`** so it outweighs the `.dark .mock-home …`
  dark-mode rescues (0,4,0), which would otherwise win.
- **Appended at the end of the file** so it wins ties on source order — the
  established constraint in this stylesheet, where ~10,000 lines sit outside
  any `@layer`.

`.rr-view` / `.rr-sort` keep their `.is-active` fill; only the non-active hover
is reset.

## Verification

| Check                                 | Result                                                                                                     |
| ------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| `webkitTapHighlightColor` on `<html>` | `rgba(0, 0, 0, 0)`                                                                                         |
| `@media (hover: none)` rules present  | 3, matching the intended selectors                                                                         |
| Desktop hover fill still resolves     | yes — `var(--mock-blue)` (light), `var(--color-gold)` (dark) both still matched on a hover-capable pointer |
| Resting background, no interaction    | `rgba(0, 0, 0, 0)`                                                                                         |

## Contracts

### Desktop

- Hover fills are unchanged on any hover-capable pointer.
- `:focus-visible` styling is unchanged everywhere.

### Mobile

- No browser tap-highlight rectangle on any control.
- No control remains filled after the tap that activated it.
- The active view/sort toggle keeps its `.is-active` fill.

## Acceptance criteria

- [x] `-webkit-tap-highlight-color` resolves to transparent
- [x] Hover fill does not persist on a hover-less pointer
- [x] Keyboard focus ring preserved (`:not(:focus-visible)`)
