# F-134: One owner for the page scroll lock

## Metadata

- Feature ID: F-134
- Category: Platform
- Owner: founder
- Status: shipped (2026-08-18)
- Decision: SA-088
- Surfaces: every overlay and sheet

## Problem — backlog #59

Seven components each did their own naive save/restore of
`document.body.style.overflow`. Because every one captured "the previous value"
at its _own_ open, nested opens leaked:

```
menu opens        → saves ''        → sets hidden
search opens      → saves 'hidden'  → sets hidden
menu closes FIRST → restores ''     → THE PAGE SCROLLS BEHIND OPEN SEARCH
```

Reachable in **two taps** on mobile: the search button sits outside the menu
panel, so tapping it closes the menu and opens search in the same tick.

An eighth site made it worse — `page.tsx` cleared `overflow` **unconditionally
on mount**, so navigating home while any overlay legitimately held the lock
silently unlocked the page underneath it.

## Fix

`src/lib/use-scroll-lock.ts` — depth, not cleverness. The **first** lock
captures the real previous value; nested locks only increment; the **last**
release restores. A component closing out of order can no longer speak for the
whole page.

Migrated: `ArtworkLightbox`, `FirstRunIntro`, `NarrationChapters`,
`TransportSheet`, `GenerationPaywall`, `GlobalSearchOverlay`. The homepage reset
is now guarded on `isScrollLocked()`, so it still clears the stale state it was
written to catch and nothing else.

`ArtworkLightbox` was the worst of the seven: it reset to `''`
_unconditionally_, including on close, so a lightbox opened over another overlay
unlocked the page for that overlay too.

The search overlay also loses its `visibilitychange` / `pageshow` re-assert —
that existed to paper over exactly this class of stomp and has nothing left to
defend against.

## Deliberately still `body { overflow: hidden }`

This change is about **ownership, not mechanism**, and the limitation is
recorded in the source rather than left to be rediscovered: the scrolling
element here is `<html>`, so on some platforms the page can still be moved.
Locking `<html>` instead _does_ hold — and breaks `position: sticky` on the
topbar, measured at bottom 53px → **−1346px** in F-118. Changing the mechanism
is a separate decision with its own testing.

## Verified

In the browser, at 390px, running the real two-tap sequence:

| Step                                        | `body.overflow`                      |
| ------------------------------------------- | ------------------------------------ |
| start                                       | `''`                                 |
| menu open                                   | `''` (no lock by design since F-118) |
| tap search — menu auto-closes, search opens | **`hidden`**                         |
| search closed                               | `''`                                 |

Plus four unit tests, including the out-of-order close and "restores what was
there before the first lock, not an assumed default".

## Acceptance criteria

- [x] Nested opens hold the lock until the last releases
- [x] Out-of-order close cannot unlock the page
- [x] Pre-existing `overflow` value restored, not an assumed `''`
- [x] Homepage reset only clears an unowned lock
- [x] Type-check, lint, 2,101 tests and a real Workers build green

## Contracts

### Desktop

- Overlays lock and release without fighting each other.

### Mobile

- The menu → search two-tap sequence keeps the page locked behind search.
