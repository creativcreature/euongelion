# F-142: Listening position survives leaving the reading

## Metadata

- Feature ID: F-142
- Category: Reading surfaces
- Owner: founder
- Status: wip
- Decision: SA-096
- Surfaces: `src/lib/audio/listening-progress.ts`, `src/components/NarrationPlayer.tsx`

## Problem

Founder approved the audio-forward plan (`docs/plans/AUDIO-FORWARD-STRATEGY.md`,
`docs/audio/AUDIO-UX-PATTERN-RESEARCH-2026-08-19.md`) on 2026-08-19. Stage 1 of
that plan is continuity: nothing above it — continue-listening, queues, The
Quiet Hour — can be built on a position that is not reliably recorded.

The strategy asserted three continuity defects. **Each was verified against the
code before any was fixed, and one of the three turned out not to be a defect.**

1. **Position is not written on client-side navigation.** `NarrationPlayer`
   flushes on `pagehide` and `visibilitychange`. Neither fires when Next swaps
   routes, and the effect cleanup removed its listeners without saving. Tapping
   from one devotional to another — the most common way a reading ends — lost
   everything since the last throttled write, up to thirty seconds.
2. **The server-write throttle was shared across readings.** `lastPushAt` was a
   module-global timestamp, so finishing one devotional and opening another
   inside 30s meant the new reading's first write was swallowed by the previous
   reading's window. Queues make this worse, because they move between slugs
   constantly.
3. **Not a defect.** The strategy claimed the `ended` flush writing
   `seconds: 0` would make finished tracks read as unstarted. Position 0 on
   completion is deliberate — it is what makes a finished reading restart from
   the beginning — and `upsertListeningProgress` sets `completed_at` on `ended`
   and keeps it ("once completed, stays completed"). Nothing is lost. The real
   obligation is on the future continue-listening query, which must filter on
   `completed_at` rather than infer completion from position. Recorded here so
   it is not "fixed" later by someone reading the same claim.

## Solution

**Per-slug throttle.** `lastPushAt` becomes a `Map<string, number>` keyed by
slug. `__resetThrottle()` clears it.

**Flush on unmount.** A dedicated effect with empty deps flushes on the way out,
reading the newest `flushProgress` from a ref so it fires exactly once rather
than on every dependency change.

**A position snapshot, because the element is gone by then.** The first
implementation of the unmount flush recorded nothing, and the test caught it:
React detaches refs before running passive effect cleanups, so `audioRef.current`
is already `null` at that moment. `flushProgress` now falls back to a
`lastKnown` ref updated on every `timeupdate`. This is also the more honest
design — it does not depend on React's teardown ordering.

The existing guard against recording a bare open (`!hasStarted &&
listenedSince <= 0`) is unchanged and still applies on unmount.

## Platform Contracts

### Desktop

- Navigating between readings client-side records the position before unmount.
- Two readings played within 30s of each other each reach the server.

### Mobile

- `pagehide` and `visibilitychange` behaviour is unchanged; backgrounding and
  lock still flush through `sendBeacon`.
- The unmount flush uses the same beacon path, so it survives a route change
  that begins a teardown.
