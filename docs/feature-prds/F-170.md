## User Expectation

- A reader who starts the Soul Audit on a weekend reads the day-0 primer and
  marks it complete like any other day. It stays complete when they come back.
- The reader is never shown an internal validation string as an answer to
  pressing a button.

## 10/10 Definition

- Every day the reader can open, the reader can finish — no day exists that
  renders a MARK DAY COMPLETE control which cannot succeed.
- Completion of the onboarding day survives a reload, because it is a row in
  the database and not a fact the browser is holding.
- The confirmation names the day in the vocabulary the rest of the reader uses
  for it ("Onboarding"), not by an index the reader never sees.
- Widening the accepted day range does not widen what counts as a valid
  request: an absent day number is still absent, not day 0.

## Scope

### In scope

- `/api/soul-audit/complete-day` POST and DELETE accept day 0 through 7.
- Presence-checked parsing of `dayNumber` so the widened floor cannot turn a
  missing field into a valid day 0.
- Day-0 completion confirmation copy in the plan reader.

### Out of scope

- The `deepen` route's `dayNumber < 1` bound. Day 0 renders through
  `OnboardingEditorial`, not the tiered path, so it never reaches that route.
- Plan-completion accounting on `/today`, which deliberately counts only
  `day >= 1` and is unaffected.
- The unapplied migration 016 (`onboarding_variant` / `onboarding_days`),
  which is a separate schema-drift item.
