# F-157: A completion you can take back

## Metadata

- Feature ID: F-157
- Category: Platform
- Owner: founder
- Status: shipped (2026-08-19)
- Decision: SA-111
- Surfaces: /devotional/[slug], /today (curated series), /library

## Problem

Founder, 2026-08-19: _"i accidentally marked one and now cant go back"_.

Marking a day read wrote to **three** places — `localStorage`, the account's
`user_progress` row, and `active_series.current_day` — and **none of them had an
inverse**. There was no unmark function, no DELETE on `/api/reading-progress`,
and no repository delete.

An action a person can take by accident, on a surface built for one-handed use
at 6am, needs a way back. Without one the product is telling the reader their
mistake is permanent — on every device they own.

## Fix

The whole chain, in reverse:

| Layer      | Added                                          |
| ---------- | ---------------------------------------------- |
| Repository | `deleteReadingCompletion`                      |
| API        | `DELETE /api/reading-progress?devotionalSlug=` |
| Sync       | `removeReadingCompletion`                      |
| Day        | `rewindActiveDayAfterUnmark`                   |
| Progress   | `unmarkDevotionalComplete`                     |
| UI         | **MARK AS UNREAD** on both readers             |

**Local-only removal would have been worse than nothing.** The next reconcile
pulls the completion back, so an undo that stopped at `localStorage` is not an
undo — it is a delay. All three writes are reversed.

The day rewind only ever moves **backward**, and only for the active series.
Un-marking a day the reader is already past changes nothing; they are re-reading
and their place is theirs.

Deleting rather than tombstoning: `user_progress` answers "has this been read",
and a row saying "no" is the same as no row — except it would then have to be
filtered out of every count, standing and reconcile. The reconcile already treats
absence as not-read.

The control is offered quietly — a text link, not a second CTA. Undo should be
findable, not competing with the thing it undoes.

## A second bug, found and fixed in the same pass

The Library had **two sources of truth in one view**. The ACTIVE card resolved
its CONTINUE from the server's `active_series.current_day`; the SAVED cards
resolved theirs from actual completions. Those agree until they do not — a failed
server write, or days finished out of order — and then two cards in one view
point at **different days for the same series**, which is worse than either
answer alone.

Completions now win everywhere, with the server day as the fallback for a series
with nothing marked yet. Completions are the reader's own record and the thing
they can actually see.

## Verified

`__tests__/unmark-devotional-complete.test.ts` — 6 tests:

- a marked day un-marks and stops reading as read
- **other days are untouched** — undo is not a reset
- the account removal is attempted, because local-only would be reverted
- the day rewind is attempted
- un-marking something never marked is a **quiet no-op**, not a spurious write
- the removal is **persisted**, so it survives a reload

Type-check clean; 13 tests green across the three progress suites.

## The plan path — finished 2026-08-19

`/today` has two readers, and the first pass only fixed one. The Soul Audit plan
reader (`DailyBreadView`) had the identical gap: MARK DAY COMPLETE with no way
back. Leaving it there would have repeated exactly the failure this project
already made once — half a fix landing and looking finished.

Different data model, same problem. Completion there is a `completed_at`
timestamp on `devotional_plan_days`, so the inverse is **nulling it** rather than
deleting a row: the plan day must survive because it carries the day's generated
content, and an absent timestamp is already how every reader of that table spells
"not finished". `DELETE /api/soul-audit/complete-day` mirrors POST's session
check, plan-ownership verification and 1–7 bound — an undo is a write.

The subtle half is local state. Completing deliberately avoids a reload, because
a reload loses scroll and motion, so the component keeps a session-local set of
completed days. An undo therefore needs a **symmetric override**: the `dayRecord`
that came down with the plan still carries the old timestamp, so clearing the
"completed" set alone would leave the UI insisting the day is done. A
`localUncompleted` set now mirrors `localCompleted`, and **the reader's position
chip respects it too** — otherwise `planCurrentDay` would keep pointing past a
day they had just taken back.

Verified by `__tests__/daily-bread-uncomplete.test.tsx`: the control appears only
once there is something to undo, the mark control returns after undoing, and the
request is a **DELETE** for that plan and day rather than a second POST.
