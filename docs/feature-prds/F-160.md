# F-160: One audio element, site-wide

## Metadata

- Feature ID: F-160
- Category: Reading surfaces
- Owner: founder
- Status: shipped (2026-08-19)
- Decision: SA-115
- Surfaces: `src/components/NarrationPlayer.tsx`, `src/components/audio/GlobalAudioHost.tsx`

## Problem

`GlobalAudioHost` mounts an `<audio>` in the root layout so playback survives a
route change. `NarrationPlayer` rendered its own as well. On a devotional page
that is **two independent playback engines on one screen**: whichever element a
control happened to hold was the one that answered, and a queue sounding through
the global element kept playing when the reader pressed play on its own. There
is no arrangement of two media elements that behaves correctly.

This was logged as open at the end of SA-097 and stayed open through five
subsequent decisions.

## Built test-first

This is the first piece of audio work in this sequence written under TDD, and
the process caught things review had not.

**RED.** A test rendering the host and the reader together, asserting one
`<audio>` in the document. It failed with `expected …(2) to have a length of 1
but got 2` — the right failure, for the right reason.

**GREEN.** `NarrationPlayer` adopts the layout's element through
`useSyncExternalStore(subscribeAudioElement, getAudioElement)` and keeps
`audioRef` pointed at it, so all thirty-odd existing `audioRef.current` call
sites work unchanged. The element's JSX props became listeners, because the
element belongs to the layout now and the panel is a view onto it. `src` is
assigned only when it differs, so arriving on a reading already sounding does
not restart it, and `loadedmetadata` is invoked directly when the element is
adopted mid-life, since that event will never fire again.

**What the full-suite gate caught.** Fifteen existing tests broke. They rendered
the reader alone, and with no host there was no element to adopt. That is a real
consequence: the reader now depends on the layout providing the element.

Their **setup** was updated to mount the host — the assertions were not touched.
Two were the exception and are worth recording: they proved "it fell back to
synthesised speech" by asserting no `<audio>` existed. That proxy is dead, since
the element is always present now. They assert the real thing instead — a player
rendered, but without the seek slider that only narration has.

## Platform Contracts

### Desktop

- Exactly one `<audio>` in the document on every route, including a devotional.
- Opening a reading while a queue is sounding does not start a second stream.

### Mobile

- Unchanged. The same single element serves lock-screen transport and the
  Media Session metadata the host owns.
