# F-124: The narration library was mastered to peak, not loudness

## Metadata

- Feature ID: F-124
- Category: Platform
- Owner: founder
- Status: shipped (2026-08-17)
- Decision: SA-080
- Surfaces: `public/audio/` (535 tracks), `src/data/audio-manifest.json`, `scripts/normalize-audio.mjs`, `public/sw.js`

## Problem

The founder reported the narration playing quiet with the volume maxed. The
player was not at fault.

Every track was levelled to **peak** instead of **loudness**. True peak sat
pinned at 0 dBTP while integrated loudness ran **−19.7 to −22.7 LUFS**, well
under the −16/−17 LUFS podcast range. That combination produces a waveform that
looks completely full and plays quiet, which is exactly the reported symptom.

Measured across the library, **73 of 535 files were not merely maxed but
actually clipping** — true peak above 0 dBTP, with `bible-365-day-1` at +0.55.

## What shipped

Two-stage normalisation, at **−17 LUFS** — the level the founder chose by ear
from a three-way A/B (−22.6 current / −17.0 / −16.3). Pass 1 measures, pass 2
applies a fixed `volume` gain and an `alimiter` ceiling. Gain owns loudness, the
limiter owns peaks, and neither rides the signal.

Verified independently across all 535 files with `ebur128` (a different filter
from the `loudnorm` that targeted them):

| Metric         | Result                             |
| -------------- | ---------------------------------- |
| Loudness       | −16.50 .. −17.30 LUFS (target −17) |
| True peak      | −1.00 .. −3.90 dBTP (gate ≤ −1.0)  |
| Lift           | +2.4 .. +6.1 dB                    |
| LRA delta      | −0.52 LU mean                      |
| Duration drift | −0.09 .. −0.04 s                   |
| Clipping       | 73 → 0                             |

## Why not the obvious approach

**Single-pass `loudnorm` was tried and rejected.** It reports
`normalization_type: dynamic` — it rides the level, compressing loudness range
1.2 LU on the A/B source — and its true-peak control does not hold: on
`he-cannot-deny-himself-day-1` it produced **+1.54 dBTP**, worse than the
untreated file and confirmed by two independent measurement paths.

**The real obstacle was that AAC adds true-peak overshoot above the limiter
ceiling, and it is not a stable per-file constant that can be probed once.** It
swung 3.2 → 7.9 dB on a single file as gain moved. Rendering the same filter
chain to float WAV and to AAC isolated the cause: the limiter held −1.6 dBFS in
PCM and the encoder still emitted +1.5 dBFS. A 5 ms limiter attack rides gain
sharply enough that 80 kbps AAC cannot reconstruct it without ringing past the
ceiling. At `attack=20` the same file encodes to −2.3 dBFS.

So the ceiling is not predicted, it is **solved for**: every iteration
re-encodes and re-measures the actual file, and the ceiling is re-aimed from
that render's measured overshoot.

## Traps this cost, all of which fail silently

1. **A ratcheting ceiling makes files quieter than doing nothing.** An earlier
   revision only ever lowered the ceiling. Over-limiting destroys loudness, gain
   then chases a target the limiter is holding down, and 10 files spiralled —
   `bible-365-day-227` walked to a −9.1 dB ceiling and **−18.6 LUFS**, quieter
   than untreated. Solving for overshoot is self-correcting; ratcheting is not.
2. **Gain and ceiling are coupled and can orbit the target.** Five files were
   still out after 10 full-size corrections. Halving the step after the fourth
   iteration collapses the orbit.
3. **Not every track is 24 kHz mono.** 528 are; the 7 `he-cannot-deny-himself`
   tracks are 44.1 kHz **stereo** music-scored productions. A hardcoded
   `-ar 24000 -ac 1` downmixes them and nothing in the loudness numbers reveals
   it.
4. **A flat stereo bitrate breaks the deploy, not the sound.** Those 7 are
   already 20–23 MB and Cloudflare Workers rejects any asset over 25 MiB. At
   160k they came out 27–31 MB. Bitrate is now derived per file from its own
   duration against a 20 MiB budget, with a hard 25 MiB guard that deletes
   rather than ships. The budget is deliberately well under the limit: the
   encoder delivers ~8% more than nominal `-b:a` plus container overhead.
5. **`?v=${bytes}` is the only cache-bust.** `/audio/*` is served
   `max-age=31536000, immutable`, and `getNarrationTrack()` versions the URL
   solely from `track.bytes`. Swapping files without re-stamping the manifest
   leaves every already-cached listener on the quiet masters for a year — the
   re-master would be invisible to precisely the heaviest users.
6. **A truncated file still measures a perfect −17 LUFS.** Loudness and peak
   checks cannot detect content loss, so verification compares duration, sample
   rate and channel count against each original.

## Standing rule

**An unverified render is not a result.** The script accepts a file only on that
file's own post-encode measurement, and deletes any file it cannot verify rather
than writing it. Every failure in this work surfaced as a missing file and a
loud complaint, never as a bad master reaching the library.

## Surface contracts

### Desktop

Narration plays at −17 LUFS through the existing `NarrationPlayer` transport.
No UI changed. The only client-visible difference is the track URL, which now
carries a new `?v=<bytes>` stamp so an already-cached reader re-fetches instead
of keeping the quiet master.

### Mobile

Identical audio and identical URL behaviour. The louder master matters most
here: phone speakers and the lock-screen transport were where "volume maxed and
still hard to hear" was reported. Peaks are held at or under −1.0 dBTP so the
lift cannot introduce distortion on small drivers, and the 7 stereo
music-scored tracks keep 44.1 kHz stereo rather than being downmixed.
