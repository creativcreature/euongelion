# F-092: An existing highlight is editable — recolour, note, remove

## Metadata

- Feature ID: F-092
- Category: Reading experience
- Owner: founder
- Status: in progress (2026-08-15)
- Decision: SA-046
- Surfaces: `/devotional/[slug]` (`TextHighlightTrigger`)

## Problem

> the highlight feature doesnt work on desktop. I can highlight text, but not
> change colors or make notes etc. i am also signed in.

## What was actually wrong

The colours were never broken. Reproduced on production against
`looking-at-the-sun-day-1`:

| Step                                          | Result before                        |
| --------------------------------------------- | ------------------------------------ |
| Select text → toolbar appears                 | ✅ works                             |
| Click a swatch → active swatch changes        | ✅ works (`active 0 → 3`)            |
| Press Highlight → mark painted in that colour | ✅ works (`reader-highlight--pink`)  |
| **Click the existing highlight**              | ❌ **no toolbar** (`count: 0`)       |
| **Re-select the highlighted text**            | ❌ **no toolbar** (`count: 0`)       |
| **Any note / edit / delete control anywhere** | ❌ **none** (button scan returned `[]`) |

There was no *second act*. `handleSelection` returns early for any selection
anchored inside `.reader-highlight` — a guard that correctly prevents nested
highlights, but which left a mark completely inert once made. Being signed in
was incidental; the same was true signed out.

`/api/annotations` already had `PATCH` (style + body by `annotationId`) and
`DELETE`. **This was a missing surface, not a missing feature**, and nothing
server-side changed.

## Scope

**In:** clicking a mark opens the toolbar against it; swatches recolour in
place; a note composer writes to `style.note`; Remove unwraps the mark and
deletes the row; noted passages are dotted-underlined; device-kept highlights
edit via localStorage; the toolbar prevents default on mousedown so the
selection survives.

**Out:** the Soul Audit; the sticky-note layer; notes as a separate
`annotationType` (a note here belongs to its highlight).

## Design decisions worth keeping

- **Paint first, reconcile after.** The mark repaints the instant a swatch is
  pressed, matching SA-038's rule that the reader's action lands visibly whether
  or not the network does.
- **Notes live in `style.note`, not `body`.** `body` already carries the anchor
  text and hydration falls back to it (`anchor_text || body`), so a note stored
  there would be indistinguishable from its anchor on restore. `style` is ours,
  `PATCH` accepts it, and colour and note then travel one path.
- **A noted passage is visibly noted.** Dotted underline, so notes are findable
  by eye instead of by clicking every mark in the reading.
- **Removing a highlight is not removing the reading.** `unwrapMark` reinserts
  the child nodes and calls `normalize()`, so the text is byte-identical and a
  later selection of that passage still matches as one run.
- **Device-kept highlights edit too.** The same control must not behave
  differently depending on something the reader cannot see.

## Acceptance criteria

- [x] Clicking a highlight opens a toolbar with Note / Ask / Remove
- [x] Swatches recolour an existing highlight in place and persist (`PATCH`)
- [x] A note can be written, is saved, and marks the passage visibly
- [x] Remove deletes the row and leaves the text intact
- [x] Signed-out highlights recolour without an API call
- [x] Verified end-to-end in the Workers runtime (`npm run preview`), not just
      in jsdom
- [x] 6 tests; type-check clean; lint 0 errors
- [ ] Deployed and live-verified

## Risks

| Risk                                        | Mitigation                                                                                     |
| ------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| Click-to-edit competes with text selection  | The handler only fires on a `mark.reader-highlight`; a drag that selects still runs the create path. |
| Toolbar click collapses the selection       | `onMouseDown` prevents default on the toolbar.                                                 |
| A failed delete resurrects the mark on reload | That is the honest outcome — the row still exists — rather than a silent local-only removal.   |
