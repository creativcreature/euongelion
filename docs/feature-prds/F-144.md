# F-144: Audio moves to R2, and seeking actually seeks

## Metadata

- Feature ID: F-144
- Category: Platform
- Owner: founder
- Status: shipped (2026-08-19)
- Decision: SA-098
- Surfaces: `src/app/audio/[file]/route.ts`, `src/lib/audio/range.ts`, `wrangler.jsonc`, `scripts/upload-audio-to-r2.sh`, `scripts/strip-audio-from-assets.mjs`, `public/_headers`

## Problem

Founder green-lit R2, 2026-08-19. Two defects, one project.

**Seeking downloaded the whole track.** A real `GET` carrying
`Range: bytes=1000000-1000999` against a 7.4 MB reading returned `200` and the
entire body — measured on the live site and on the origin worker, cache hit and
all. The cause is that Cloudflare's static-asset layer does not implement 206
Partial Content. `public/_headers` advertised `Accept-Ranges: bytes` regardless,
so every browser was told seeking was cheap while each scrub refetched the
reading. Chapters and queues both multiply seeking, so this was going to get
worse as the audio-forward work landed.

**The catalogue lived on one laptop.** 380 of 550 tracks are gitignored, so they
existed only on this machine plus whatever was deployed. A build from a fresh
clone or from CI would have shipped a site whose audio genuinely 404s, and those
files could not be reconstructed without re-rendering all of them.

## Solution

**All 550 tracks uploaded to the `euangelion-audio` R2 bucket** (3.70 GiB) via
`scripts/upload-audio-to-r2.sh`. The script is idempotent against a local ledger
because wrangler 4.110 has no `r2 object list`; it retries once per file and
exits non-zero when the ledger is short, which is how the one failed upload in
the first run was caught and finished on a re-run.

**A route serves them with real ranges.** `src/app/audio/[file]/route.ts` reads
from R2, which supports byte ranges natively, and returns 206 with a correct
`Content-Range`. Verified in the Workers runtime: 1000 bytes requested, 1000
received; a suffix range returns the last N bytes; a full GET is byte-identical
to the file on disk.

**Audio is removed from the asset bundle before deploy.**
`assets.run_worker_first` is supposed to hand `/audio/*` to the Worker and,
measured on wrangler 4.110, does not — a request for a track that exists as an
asset never reached the route, while a request for one that does not reached it
fine. `scripts/strip-audio-from-assets.mjs` deletes the directory after build,
which is what actually hands the path over. Two things fall out: deploys stop
uploading 3.70 GiB every time, and Cloudflare's hard 25 MiB per-asset limit
stops applying to tracks at all — which was going to block any scored re-render.

**The fallback is labelled, never silent.** A key missing from R2 still serves
from the asset bundle, carrying `x-audio-origin: assets-fallback`, so an
incomplete upload is visible in one curl instead of hiding behind working audio.

## Platform Contracts

### Desktop

- Range requests return 206 with an accurate `Content-Range`.
- A full request is byte-identical to the master.

### Mobile

- iOS media elements issue suffix ranges when a listener drags to the end;
  `bytes=-N` returns the LAST N bytes, which is covered by test — reading it
  forwards would silently replay the opening of a reading.
- `Accept-Ranges: bytes` is now truthful rather than advertised in hope.
