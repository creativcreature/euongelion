# F-143: Audio survives the route, and a queue plays on

## Metadata

- Feature ID: F-143
- Category: Reading surfaces
- Owner: founder
- Status: wip
- Decision: SA-097
- Surfaces: root layout, `/series/[slug]`, `/library`, `src/components/audio/*`, `src/stores/audioStore.ts`

## Problem

Founder, 2026-08-19: _"push through the plan to the very end."_ Stages 2 to 5 of
the approved audio-forward plan — lift the transport above the routes, a global
bar, queues with auto-advance, and listening in the library.

Two founder rulings govern the shape:

- _"its ok that a person binge a series, it means the material is really working
  for them. That is why I want an extreme breadth of content."_ So auto-advance
  is on for every queue kind, and the store must never encode a per-source
  stopping rule.
- Listening lives in `/library`, per the founder's placement instinct. The
  library holds **your** listening; discovery of **new** listening is a separate
  job and is not built here.

Before this, a media element rendered inside the reader was destroyed whenever
Next swapped routes, so audio could not survive leaving a devotional. That is
the whole reason listening felt like a feature of one page rather than a mode of
the site.

## Solution

**One audio element, above every route.** `GlobalAudioHost` mounts a single
`<audio>` in the root layout and publishes it through a module singleton
(`audio-element.ts`) rather than store state — the element is an imperative
handle, not data, and putting it in a slice would re-render every consumer on
registration.

**A persisted queue.** `audioStore` holds items, cursor, source and label. The
queue is persisted because a session that does not survive a reload reads as
broken; `playing` is deliberately excluded, since restoring it would claim audio
is sounding when nothing is, and nothing here autoplays on load.

**Auto-advance everywhere.** `ended` advances the cursor regardless of source.
The test asserts this across all four kinds so the withdrawn stopping rule
cannot return by accident.

**`GlobalAudioBar`,** shaped from what actually ships (Mobbin, 2026-08-19): a
rounded card docked above the tab bar, not a full-bleed strip. It **carries a
dismiss control**, which our own scroll bar lacked and which both Substack and
Apple News have — a bar that follows a reader everywhere with no way out stops
being a transport and becomes chrome. It retires on the reading it is playing,
because the reader's own panel is the better surface and two transports on one
screen is a bug.

**`ListenButton`** states the runtime, because what a listener needs before
committing is how long something is. It calls `play()` **synchronously inside
the tap handler**: iOS grants a media element permission to sound only from
within the gesture that asked, and awaiting anything first loses the grant.

**`ListeningSection`** puts Up Next in the library with the vocabulary every
studied queue uses — context, runtime, reorder, remove, and an empty state that
offers a route out rather than a dead end.

Queues only ever contain readings that **have a delivered track**. A queue that
hits a silent item reads as a broken player rather than a partial catalogue, so
filtering happens once in `queue-builder`.

## Platform Contracts

### Desktop

- Audio continues across client-side navigation; the bar appears once playing
  and retires on the track's own reading.
- Series pages offer Listen as a peer of the read action, with runtime stated.

### Mobile

- The bar sits above `.mobile-tab-bar`, which does not hide for it.
- All controls keep a 44px target. Below 560px the time readout hides; below
  400px the queue-step buttons hide. A control is never the first thing to go.
- Play is invoked inside the tap so iOS honours it.
