# F-135: The publishing record — byline, publication dates, and one version

## Metadata

- Feature ID: F-135
- Category: Platform
- Owner: founder
- Status: shipped (2026-08-18)
- Decision: SA-089
- Surfaces: every reading's colophon; the release process

## Problem

Founder direction 2026-08-18: _"treat this like a true publishing house."_ Three
records a publisher keeps, and this one kept none of them.

**No byline.** `AuthorColophon` has existed since 2026-05-13, styled and mounted
in both readers — and both call sites passed only `translation`, so three of its
four lines had never rendered. A component nobody noticed was doing nothing.

**No publication dates.** Not one of the 575 devotionals carried a date field,
and nothing captured one when a new reading shipped. Even a perfect backfill
would have gone stale the next morning.

**No version.** `package.json` sat at **0.7.0 since February 2026** through 88
decisions and 134 features, with **zero git tags**. The only number that moved
was a service-worker cache-buster someone remembered to type.

## Dates are graded by the evidence they rest on

Only **121 of 575** readings have a true publication day:

| Source        | Count | Quality                                                  |
| ------------- | ----- | -------------------------------------------------------- |
| `substack`    | 86    | Real publication date, one per day, Sept 2025 → Jan 2026 |
| `series-ship` | 35    | Five prefab series that shipped as a unit                |
| `first-seen`  | 454   | A bulk import — **365 share `2026-05-08` alone**         |

So each record stores its `source`, and `formatPublished()` renders an exact day
only for the first two. `first-seen` renders **the month**. Rendering a day there
would assert a publishing event that never took place, on a product whose whole
claim is being verified when the category is not.

Dead ends checked so they are not re-checked: filesystem birth times are **worse**
than git — 8 distinct dates, and 365 files stamped _later_ than their own commit;
the CHANGELOG records no per-series launches. The Substack CSV export is stale,
and five `genesis-*` posts were recovered from the live page's JSON-LD — a method
validated by reproducing a known CSV date exactly.

## The service-worker version pair had drifted nine releases

`sw.js` carries a comment demanding CACHE_NAME stay in sync with the client's
`SW_VERSION`. It was `v117` against `v108`.

The client compares `SW_VERSION` to localStorage and, on mismatch, unregisters
every worker and deletes every `euangelion-*` cache — the recovery path for a
reader whose worker is wedged. A returning reader's stored `v108` matched the
shipped `v108`, **so it never fired for nine releases**. The primary update path
still worked (the worker's own `activate` drops non-current caches), so this was
a dead safety net rather than a broken site.

Hand-editing two numbers in two languages on every deploy was never going to
hold. `scripts/release.mjs` now moves all three in lockstep and heals a drift
upward, never backward, so no reader is handed a version they already stored.
