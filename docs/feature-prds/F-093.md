# F-093: The chat scrolls, and the composer stays on screen

## Metadata

- Feature ID: F-093
- Category: Reading experience
- Owner: founder
- Status: in progress (2026-08-15)
- Decision: SA-048
- Surfaces: study chat panel (`DevotionalChat`)

## Problem

Founder: _"the chat needs to have its seperate scroll wheel, as I cannot access
the content the chat wrote out as its below my visibility."_

The message list carried `flex-1 overflow-y-auto`, which reads as correct. It
was not. A flex child inherits `min-height: auto`, which refuses to shrink
below its content — so the list **grew to fit the reply** instead of scrolling,
and `overflow-y: auto` never engaged. Everything below it, including the
composer, was pushed past the bottom of the window.

Measured in the browser with 3000px of content injected, before the fix:

```
scroller   min-height: auto   clientH 3145   scrollH 3145   scrolls: false
composer   visible: false
viewport   900
```

The list was 3,145px tall inside a 900px window. There was no scrollbar because
there was nothing to scroll — the container had simply expanded.

## Fix

`min-h-0` on the whole chain: the panel grid, the conversation column, and the
scroller itself. Fixing only the scroller is insufficient — an unconstrained
ancestor passes its full content height down, so the child never has a bounded
box to scroll within. That is why the test asserts all three.

After, at 1280×900:

```
scroller   min-height: 0px    clientH 541    scrollH 3145   scrolls: true
composer   visible: true
```

## Platform contracts

### Desktop

The message list scrolls within the panel; the composer is pinned and remains
visible regardless of reply length. Panel height is bounded by the viewport.

### Mobile

Same behaviour at 375×812 — scroller `clientH 435`, `scrollH 3145`,
`scrolls: true`, composer visible, panel bounded to 812px. No separate mobile
treatment was needed; the same three `min-h-0` guards fix both.

## Verification

Behaviour was verified by injecting 3000px into the live message list and
reading `clientHeight` / `scrollHeight` / composer position, rather than by
screenshot — a screenshot cannot distinguish "scrolled to the top of a long
list" from "container grew and clipped".

Pinned by `__tests__/chat-scroll-contract.test.ts` (4 cases), including a guard
that fails if any future `flex-1 overflow-y-auto` is added without `min-h-0`.

## Known gaps

**Study chat runs 18–19s per reply against a 30s Workers wall-clock ceiling.**
Measured twice on production: `HTTP 200 in 18.0s` and `HTTP 200 in 19.3s`. A
browser request during this work returned **504**. That is the "seems to work"
symptom — it succeeds until it doesn't. Not addressed here; it needs its own
pass. The likely contributor is `getCanonicalRagIndex()` loading the full 15 MB
`reference-index.json` on cold start; CLAUDE.md documents a 3.2 MB
`reference-index-slim.json` for exactly this reason, and that file does not
exist in the repo.
