# F-102: Notes, journal entries, and reflection answers

## Metadata

- Feature ID: F-102
- Category: Reading surfaces
- Owner: founder
- Status: wip
- Decision: SA-059
- Surfaces: `/devotional/[slug]`, `/daily-bread`, reader selection toolbar, `ReflectionModule`, `RecapModule`, `PrayerModule`

## Problem

Founder, 2026-08-16:

> "I want to add note taking feature that works similar to the highlight
> feature — maybe even works with it somehow. I also want reflection questions
> etc to take user input so users can write journal entries and such."

The catalog already ships **2,062 journal prompts** — 545 reflection modules
carrying 1,517 additional questions across 568 devotionals — and not one of them
has anywhere to write an answer. The prompts were authored, shipped, and read;
the reader has been asked 2,062 questions and given no paper.

Underneath that sat a defect that had to be fixed before anything could be built
on the same table.

## Prerequisite defect — silent data loss (fixed first)

`updateAnnotation` overwrote `anchor_text` and `body` with whatever the PATCH
carried. The highlight editor PATCHes with only `annotationId` + `style` — a
recolour, or a note — and `sanitizeOptionalText(undefined, n)` returns `null`.
So **recolouring a highlight blanked the text it was anchored to.**

Nothing surfaced at the time. The loss appeared on the next load, where
`hydrateSavedHighlights` matches a stored row back onto the page by
`anchor_text || body`: with both null there was nothing to match, the mark never
repainted, and the Library row rendered empty. The reader's highlight was gone
and no error was reported anywhere.

The distinction that fixes it is **presence, not value** — a key absent from the
request leaves its column alone; an explicit `null` still clears it.

Verified against the live table, not only in memory: insert a highlight-shaped
row, PATCH style only, read back — `anchor_text` and `body` intact, colour
applied. (The unit tests run against the in-memory store because Vitest does not
load `.env.local`, so a green suite is not by itself evidence of a real round
trip.)

## Solution

**A note is a highlight that has words on it.** There is no second note system.
The selection toolbar becomes `Highlight · Note · Ask`; Note marks the passage
_and_ opens an editor. Notes continue to live in `style.note` rather than `body`
(SA-046 §4): `body` carries anchor text and hydration falls back to
`anchor_text || body`, so a note in `body` would be indistinguishable from its
anchor on restore.

**One table, no schema change.** Every writing surface rides the existing
`annotations` table, discriminated by `style.kind`:

| Surface                   | `annotation_type` | `style.kind`                    | Anchored to             |
| ------------------------- | ----------------- | ------------------------------- | ----------------------- |
| Highlight                 | `highlight`       | `favorite_verse`                | selected text           |
| Note on a passage         | `highlight`       | `favorite_verse` + `style.note` | selected text           |
| Reflection / recap answer | `note`            | `reflection`                    | module + question index |
| Own prayer                | `note`            | `prayer`                        | prayer module           |
| Free journal entry        | `note`            | `entry`                         | the devotional          |
| Audio clip                | `note`            | `clip`                          | a timestamp             |

This is deliberate and load-bearing: `annotations` is already enumerated in
`data-export.ts`, `account-deletion.ts` and `retention-cleanup.ts`, so export,
deletion and retention work on day one. A new table would silently escape all
three. Edit time lives in `style.editedAt` because the table has no
`updated_at` column.

**Prayer gets a different control.** All 543 prayer modules pose no question —
they are prayers to be prayed, with `prayerText` and an optional `breathPrayer`.
An answer field under one misreads the form, so it gets an _Add your own prayer_
affordance: same storage, framed as writing alongside rather than answering.

**The reader's own writing never reaches the model.** Religious belief is
special-category data under GDPR Art. 9. Selecting published devotional text and
asking about it stays available; piping what the reader wrote does not.
`JournalField` has no route into the chat store, and `/api/chat` refuses an
explicitly journal-sourced payload.

## Contracts

### Desktop

- The selection toolbar offers `Highlight · Note · Ask` and flips below the
  passage when there is less than 140px of room above (SA-047).
- Reflection answers render inline beneath each question, inside the existing
  `<ol>`, preserving the module's typography and measure.
- A note editor is an anchored panel, not a tooltip textarea.
- Autosave on blur and on a 2s debounce; state reported in a `role="status"`
  region as `Saving` / `Saved` / `Couldn't save`.

### Mobile

- Every control keeps a ≥44px touch target at 375px.
- The note editor does not obscure the passage it annotates; it opens below when
  the selection sits in the upper third of the viewport.
- Fields are full-measure at 375px and never trigger horizontal scroll.
- Tested at 375 / 768 / 1024.

## Acceptance Criteria

1. A style-only PATCH preserves `anchor_text` and `body`; an explicit `null`
   still clears the column. Pinned by test and verified against the live table.
2. Highlight → recolour → reload: the mark is still painted and still coloured.
3. Every reflection prompt and additional question accepts an answer that
   survives reload.
4. Recap `integration_question` accepts an answer.
5. Prayer modules offer _Add your own prayer_, not an answer field.
6. A failed save is reported on the control; nothing is silently dropped.
7. Signed out, every writing control is visible and locked, and nothing is
   written to the database, `localStorage`, or a session-keyed row.
8. `JournalField` contains no reference to the chat store, pinned by test.
