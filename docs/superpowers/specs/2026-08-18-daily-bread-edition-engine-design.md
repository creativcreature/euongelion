# The Daily Bread — edition engine, the whole paper, and daily automation

- Date: 2026-08-18
- Decision: SA-090
- Feature: F-136
- Surface: `/daily-bread` ONLY (founder: "Fully locked to the one page tho!")
- Status: design approved in chat 2026-08-18, autonomous execution authorised

## Problem

The Daily Bread is a newspaper that repeats every ten days.

Every "daily" section is a fixed TypeScript array in `src/data/daily-edition.ts`
rotated by `dayOfYear % length`: 14 practices, 6 guides, 10 panels, 12 word
studies, 7 prayer foci. Two readers on the same morning get the same edition —
which was the goal — but a reader who returns for a fortnight has seen the whole
paper twice. It is an edition without new news.

Founder, 2026-08-18:

> "I want to drastically improve The Daily Bread. It needs new content every day.
> The cartoons are VERY bad right now. The devotional needs to be treated like a
> feature article. The entire page needs to lean extremely heavily into an
> Editorial Newspaper Magazine hybrid. More imagery, more content. Should be its
> own daily scroll hole of Good News. … Crosswords, interactives, video content,
> pull in legal and unblocked content from youtube and other christian sites,
> lining back to them. … Think a true newspaper spread, with magazine inspired
> layouts and intrigue and image usage. Very image and text as art forward.
> Dynamic daily. I dont want to have to prompt the content."

Three defects behind the headline complaint:

1. **The cartoons are off-style and off-subject.** `par-persistent-widow.webp`
   is a man in a 1940s fedora at a door in a gothic-spired Western city, lit
   with gold glow on a dark ground. The parable is a widow before a judge. It
   breaks the locked riso preamble on subject, period, region, palette and
   lighting simultaneously. `par-prodigal-pigs.webp` is closer but carries a
   gold sun and a cubist figure in modern dress.
2. **There is no content pipeline.** New content means a developer editing a
   TypeScript array and deploying.
3. **The paper is thin.** One devotional, one practice, one word, one panel,
   three guides, a prayer list. A newspaper has a puzzles page, an arts page,
   letters, and a back page.

## Constraints discovered (these shape everything)

- **Cloudflare Cron is inert.** `wrangler.jsonc` has `triggers.crons` commented
  out; the OpenNext worker exports only `fetch`, with no `scheduled()` handler.
  In-worker nightly generation is blocked behind the Phase 5 worker-wrap.
- **Auto-deploy on push to main is not reliable** (memory, 2026-06-10). Any
  design where new content requires a deploy inherits the project's riskiest
  operation daily.
- **The image library is not on this machine.** `public/images/library/` and
  `public/images/generated-*/` are gitignored; a `find` across the home
  directory returns nothing. The 1,404-entry catalog JSON survives and only 3
  entries carry `assignedTo` — that is not 1,401 unused images, it is 1,401
  absent ones. Any plan that assumes 602 riso posters is planning against
  assets that do not exist here.
- **Claude Code cannot generate imagery for this project.** CLAUDE.md is
  explicit: `image_gen` is a Codex tool; Nano Banana and Higgsfield are banned
  for this pipeline. Imagery is specified here and generated by Codex.
- **The prints carry garbled AI text.** `angelico-annunciation-believe.webp`
  has fake lettering baked into its bottom margin. Publishing unaudited is
  publishing visible gibberish.

## Architecture

### The engine

One table. One generator per section kind. One runner that serves both the
nightly Action and the monthly batch, so the command run by hand is the command
that runs unattended.

```
edition_items
  id            uuid pk
  kind          text        -- 'lead' | 'prayer' | 'word' | 'practice' | 'strip'
                            -- | 'gallery' | 'crossword' | 'unscramble' | 'quiz'
                            -- | 'screening' | 'season' | 'guide' | 'witness'
  publish_date  date        -- the edition this belongs to (UTC)
  slot          int default 0 -- ordinal within a kind, for kinds that run
                            -- more than one entry per edition (guides, screening)
  status        text        -- 'draft' | 'approved' | 'published' | 'rejected'
  payload       jsonb       -- shape validated per kind by a zod schema
  source_url    text null   -- required when the kind is third-party
  source_name   text null   -- required when the kind is third-party
  approved_by   uuid null
  approved_at   timestamptz null
  created_at    timestamptz default now()
  unique (kind, publish_date, slot)
```

RLS: public read where `status = 'published'`; write restricted to the service
role. The admin queue reads drafts through the service role only.

Generators live at `src/lib/edition/generators/<kind>.ts`, each exporting

```ts
generate(date: Date, ctx: GenCtx): Promise<EditionItem[]>
```

Pure and offline-testable — a generator reads the corpus and the catalog, never
the network. The two that must reach the network (`screening`, and `lead` on its
weekly run) are isolated behind an explicit `ctx.fetch` so the rest of the suite
runs hermetically.

Runner: `scripts/edition/build.mjs --days=N --from=YYYY-MM-DD [--kinds=a,b]`.

### Which sections need a model, and which do not

This is the load-bearing property of the design: **most of the paper needs no
LLM at all**, which is what keeps it free, reliable and genuinely daily.

**Deterministic — computed from assets we own. Written straight in as
`approved`, because there is nothing to review in a computed crossword.**

- `prayer` — a prayer from scripture, printed in full with its reference.
- `word` — Greek/Hebrew from the Strong's index.
- `crossword`, `unscramble`, `quiz` — from the Bible corpus.
- `gallery` — from the audited print pool.
- `season` — liturgical calendar.
- `witness` — the commemoration for the date, from a committed martyrology.
  **Dependency:** no such dataset is in the repo. Phase 1 commits one built from
  a public-domain source (the Roman Martyrology and the Anglican and Lutheran
  calendars of commemoration are all public domain), with the source recorded
  per entry. If that dataset cannot be assembled cleanly, the section stays
  empty and renders nothing rather than shipping invented commemorations.

- `guide` — the practical guides, seeded from the existing `GUIDES` array. A
  guide is evergreen editorial, not daily: the generator selects which run
  today, it does not write new ones.

**Generated — LLM, lands as `draft`, needs the founder's eye.**

- `lead` on its weekly net-new run.
- `practice`.
- `strip` captions.

**Third-party — fetched, lands as `draft`, never publishes unseen.**

- `screening` — allowlisted YouTube channels and Christian sites.
- Sourced prayer needs (Open Doors, Voice of the Martyrs) — attributed, linked.

### Read path and failure behaviour

`src/lib/edition/read.ts` exposes `getEdition(date)`, assembling one edition
from `status = 'published'` rows. The page keeps `revalidate = 3600`.

Per Development Rule 1 (no silent fallbacks), the two failure modes are
deliberately different:

- A **missing section** renders nothing — no placeholder, no "coming soon". This
  is F-098's existing contract and it is correct.
- A **missing database** renders a visible failure state. The page must never
  assemble a plausible-looking paper out of fallbacks when the edition could not
  be read. A broken feature looks broken.

### Automation

`.github/workflows/daily-edition.yml`, nightly. Runs the same runner with
`--days=1 --from=tomorrow`, writing rows to Supabase. Needs
`SUPABASE_SERVICE_ROLE_KEY` and `ANTHROPIC_API_KEY` as repository secrets.

No commit and no deploy is involved in publishing content, which keeps the
project's most failure-prone operation out of the daily path. If the Action
fails, yesterday's edition stays up and the queue shows the gap.

The founder's monthly-weekend fallback is the same command with `--days=30`.

## The paper

Section inventory, in reading order.

**Front page**

- **The Lead** — the devotional as a genuine feature article: kicker, standfirst,
  byline, drop cap, pull quotes. Net-new on **Sunday**, rotation Monday to
  Saturday, so the new feature lands on the day the most readers arrive.
- **The Rail** — what else is in today's edition, with thumbnails.
- **The Season** — a paper's weather box, but liturgical.

**The Word desk**

- **Word of the day** — from the lexicon index, not a 12-item loop.
- **The Practice** — one doable thing.
- **How to read** — the practical guides. Evergreen; grows slowly.

**The Funnies** — The Ninety-Nine.

**The Puzzles page** — crossword, unscramble/fill-the-gap, "where is this from?".
The most reliably daily page in the paper and the strongest return hook.

**Arts & Culture**

- **The Gallery** — the audited prints, framed as reproductions with attribution.
- **The Screening Room** — allowlisted video and articles, always linked out.

**The back page**

- **The Daily Prayer** — scripture, printed in full.
- **The Cloud of Witnesses** — a paper has obituaries; this one commemorates who
  the church remembers today. Martyrologies are documented, so this stays inside
  the invention line.
- **Letters** — real reader responses, moderated. Dormant until submissions exist.
- **Notices** — where `COMMUNITY` lives once real entries exist.

**Explicitly not built:** "On this day in church history". It is reported fact
about real people, and without a sourced dataset behind it it is exactly what
the invention line forbids.

## The invention line, restated

F-098 drew it and this design keeps it in the same place, with one improvement.

We invent **our own voice**: practices, guides, strip captions, lexical glosses.
We do not invent **other people's reported facts**.

The improvement is the prayer list. F-098's weekday categories were invented —
honestly, in our own voice, but invented. Replacing them with prayers pulled
directly from scripture removes invention from the section entirely: the text is
real, attributable, and three thousand years old. Real people to pray for return
only through sourced, allowlisted feeds with attribution — never as prose we
wrote.

## The Ninety-Nine

The flock left behind while the shepherd goes after the one, dryly commentating
on being the responsible ones nobody wrote a parable about. It is the elder
brother's complaint, which is the live nerve in this audience, and it earns wit
without ever being cheesy.

The concept was chosen partly on **character drift**, which is the hard problem
in an automated strip: the same cast must survive hundreds of generations, and
one fedora already wrecked the current panels. Sheep are simple high-contrast
silhouettes with no faces to drift and no period costume to get wrong.
Consistency stops being a fight.

Deliverables, in order:

1. A locked character sheet — three to four sheep with distinct silhouettes
   (a bell, a notched ear, a lamb), specified against the riso preamble.
2. Prompts assembled by `scripts/imagery/build-prompts.mjs`, never hand-written,
   with the four founder-approved anchors attached as references on every
   generation.
3. Codex generates the bank. Claude specifies; Claude does not generate.
4. Captions written per panel and stored as `strip` payloads.

The 10 `par-*.webp` panels are retired from the daily slot.

## The Gallery and the print audit

The audit covers the 291 tracked prints in `public/images/devotional-prints/`
— the pool the site can actually serve. All 291 were VISUALLY inspected
(fifteen parallel agents opened every file) and verdicted
`clean | text-artifact | unusable` with a reason each, recorded in
`docs/print-audit-2026-08-18.json`. The Gallery generator draws only from
`clean` (145 prints — five months of dailies). The 643-directory archive at
`archive/devotional-prints/` (662 MB, not served) is the later expansion pass:
same JSON, same visual method, before any of it reaches the page.

Each Gallery entry publishes as a reproduction, not decoration: artist, title,
date, and one paragraph on what to look at. The frame is the point — it is what
turns a Renaissance chromolithograph sitting inside a cobalt-and-cream riso brand
from an inconsistency into an arts column. A newspaper runs an editorial cartoon
and a reproduction of a masterwork on facing pages and nobody calls it
incoherent; register shifting by section is what a paper does.

## The Screening Room

Replaces `src/app/admin/youtube-allowlist/page.tsx` and
`src/app/admin/feed-controls/page.tsx`, which are dead mockups — hardcoded
arrays, buttons with no handlers, and at least one fabricated channel id. They
violate Development Rule 6 as they stand.

- `edition_sources` table: name, kind, channel/feed id, enabled, added_by.
- A fetcher resolves new items from enabled sources into `screening` drafts.
- `/admin/edition` approves in bulk.
- A global kill switch disables all third-party rendering in one flip.
- Every published item carries `source_name` and `source_url`. Attribution is a
  NOT NULL constraint, not a convention.

## Phasing

Each phase ships independently; nothing waits on the phase after it.

1. **Engine** — migration, generators, runner, read path, `/admin/edition`. The
   paper looks identical, now fed by the pipeline. De-risks everything after it.
2. **The spread** — the full editorial/magazine layout overhaul.
3. **Puzzles** — crossword, unscramble, quiz.
4. **The Gallery** — the print audit, then the section.
5. **The Screening Room** — sources, fetcher, queue, kill switch.
6. **The strip** — character sheet, Codex bank, publish.
7. **The weekly net-new lead.**
